I built a support assistant, then tried to catch it out

A customer-support assistant for a pretend shopping platform — refunds, returns, order lookups. Building it took an afternoon. Testing it taught me considerably more.

Part one

What I did

  1. 1 Filled in the five missing lookups. The assistant could already talk. What it couldn't do was fetch a policy document, search the catalogue, list someone's orders, cancel an order, or track down an order from a vague description like "the vase I bought last month".
  2. 2 Held 15 real conversations and wrote down every one. As a shopper, as a shop owner, and as support staff — including the awkward cases: a refund that's too old, a refund too big to approve automatically, someone asking after an order that isn't theirs.
  3. 3 Built a sixth lookup because a conversation demanded it. Asked "how many days do I have left to return this?", the assistant had to admit it didn't know today's date. So I gave it something that answers exactly that.
  4. 4 Found one instruction worth changing — and three that weren't. I had four suspicions about vague instructions. Testing showed three were already handled. I changed one sentence and re-ran the same conversation to prove it mattered.
Part two

What I learned

The idea underneath everything

Writing a rule down doesn't make it real

There's a document describing how this assistant should behave. The assistant never reads it. Nothing written there has any effect until a person copies it into one of three places — and those three places offer completely different guarantees.

On privacy

Rules that matter can't be polite requests

A shop owner asked to see an order belonging to a different shop, and was refused — but not because the assistant had been told to refuse. The refusal happened in code, before the assistant was consulted. It was never asked its opinion, so there was nothing to talk it out of.

On vagueness

What you hand it decides what it can honestly say

A shopper asked whether she could return an old order. The lookup came back with a bare yes-or-no: not eligible. No dates, no reason. So the assistant did the only thing left to it and guessed out loud.

Before

"This could be due to the return window having closed or a store-specific policy."

After

"The 30-day window expired on June 16 — it's been 45 days since delivery."

Nothing about the assistant changed between those two answers. I added a lookup that returns the reason alongside the verdict, and the waffle disappeared. When a system sounds evasive, the first honest question is whether it was given enough to be specific.

On changing things

Only edit the instructions when you can point at the failure

I had four theories about instructions that were missing or too vague. Three were wrong — the assistant already handled those situations well, and "fixing" them would have been editing on a hunch.

  • held upNobody tells it today's date — it said so plainly rather than inventing one.
  • held upNothing says account changes need a person — it passed the request to one anyway.
  • held upHanded a broken record with a missing delivery date, it named the gap instead of papering over it.
  • failedIt credited policy documents it read, but not policy facts that reached it another way.

Only the last earned an edit: one sentence. Re-running the identical conversation afterwards, it started crediting the source properly — and went and fetched the document first, which I hadn't asked for.

On my own mistakes

Two things I was confidently wrong about

I was sure I'd caught a bug. A shopper asked for a $240 refund and the assistant seemed to stall. It hadn't — it was asking why she wanted the refund, because it needs a reason to file one. A turn in the middle of a conversation isn't a verdict.

I was sure refunds needed approval above $50. The real figure is $100, and it lives in exactly one file that every quoted number traces back to. Checking took ten seconds; not checking would have put a false failure in my notes.

The best thing I found

A policy can be published everywhere and still not exist

One shop charges up to 15% on opened items. It's on the shop's public policy page, it's in the platform's fee policy, and the database has a column recording that this shop opted in.

No code anywhere reads that column.

So the assistant told one shopper she'd get 85% back on an opened item — correct, and well-sourced. Then it refunded another shopper the full $56.75 on an opened item from the same shop. Same system, same afternoon.

I left it broken deliberately. The rule isn't defined well enough anywhere to implement without inventing it, and an improvised fix would have quietly broken the yardstick the later coursework measures against. Writing down a real gap beats patching an imagined one.

Where it ended up. Five lookups written, a sixth added because a conversation demanded it, fifteen recorded conversations across three kinds of user, and one evidence-backed edit to the instructions.
