Evaluating and Improving AI Agents · Homework 1–7

How to find, test and monitor what an AI agent gets wrong

A walkthrough of seven course assignments, built on one practice agent: a customer-support assistant for a fictional online marketplace. Each step below shows what I did, what it produced, and a mock-up of what it looked like — following one real conversation the whole way through.

250planned test conversations
7failure types named by hand
10automated tests on every change
50conversations monitored before vs after
Words used below
TraceThe recording of one conversation: every message, tool the agent used, and what the tool returned.
ScenarioA planned test conversation: who the customer is, what they ask, and what should happen.
Failure modeA named, yes/no type of mistake, e.g. “sends the customer elsewhere”.
Grader (LLM judge)An AI given written instructions to mark a conversation Pass or Fail for one failure mode.
Code checkA simple program check for an exact fact, e.g. “no refund was created”.
Regression / capabilityA test that must keep passing vs one the agent can't do reliably yet.

Homework 1–2

Build the agent, and record everything it does

What I didFilled in the support agent's tools (look up orders, check return eligibility, refund, cancel, escalate) and put it behind a server that logs every request to Langfuse.
What came outA working agent where the tools enforce the rules (a refund over $100 waits for a person), and a trace for every conversation.
Langfuse · one trace
tracesupport-0007· shopper 206 · prompt version stamped
 ├ model reads the message, decides to look up the order
 ├ tool check_return_eligibility(order 9839) → eligible, 16 days left
 └ model writes the reply to the customer

A trace is one conversation turn; each step inside it (model call, tool call) is recorded with its inputs and outputs. Without this, there is nothing to evaluate later.

Homework 4

Read conversations and write down what's wrong

What I didBuilt my own annotation UI that shows each conversation's full trajectory as one linear timeline: customer message, tool call, tool result, agent reply, in order. Then open coding: read conversations one by one, highlighted the exact words that bothered me, and wrote a note in my own words. No categories yet.
What came out95 notes across the conversations I read. Conversations with nothing wrong got a note too.
my annotation UI · support-0001 · the trajectory, top to bottom
1 · customeri need help with taxes on stuff i resold through cartwheel. i have no idea what forms i need or what info to pull…
2 · tool call search_help_center(“taxes reselling seller tax forms”)
3 · tool result cw-account-security: “…Requests for legal advice are outside support's scope…”
4 · agent replyI hear you… but tax advice falls outside what I'm able to help with as Cartwheel support. Here's what I can do and what I'd recommend: 1. Order & earnings history…
my note, pinned to the highlighted wordsShould not give alternative guidance to their solution on something that is out of scope. We def should not give any tax/legal advice nor mention stuff we don't have documentation to back.
5 · customer (follow-up)i still havent gotten a real answer here…

Seeing the tool calls and results in line is what makes a judgement possible: here the policy lookup said legal advice is out of scope, and the reply still offered alternatives. Categories come later, from the notes.

Homework 4

Group the notes into named failure modes

What I didAxial coding: grouped notes that one fix would solve. Gave each group a name, a yes/no test someone else could apply, and “close negatives” — examples that look like the failure but aren't.
What came out7 failure modes. The two most common in the first 31 conversations: unrequested narration and padding (13), and sending customers elsewhere or inventing a procedure (8).
my notes (four of them)“Don't suggest an alternative place to look for answers. Just say you cannot answer.”
“Shouldn't assume route to fix in UI that it doesn't know about.”
“Made up — no policy supports refuse delivery.”
“Made up, nowhere do we say that reaching out to stores through store page is possible.”
→
failure modescope_handling_overreach Yes/no test: on a request Cartwheel can't serve, does the reply point outside Cartwheel or invent a procedure no policy describes? Close negative (not a failure): declining a card change and pointing to Cartwheel's own account settings — that one is real policy.

Homework 5

Build an automated grader, and measure how often it's wrong

What I didWrote instructions for an AI grader (an “LLM judge”) that reads a whole conversation and answers Pass or Fail with a reason. Split my 71 labels three ways before writing anything, then hill-climbed the prompt: run it on the practice set, read every disagreement with my labels, revise, run again. Froze the best version and sat the locked exam once.
What came outA frozen grader plus its two error rates — how often it passes good replies, and how often it catches real failures. Exact facts get simple code checks instead.
the grader reading support-0003
You are an evaluator for Cartwheel… FAIL if any assistant message directs the user to an outside party as the solution… --- Trace to evaluate --- user: i need this letter i got translated into spanish… assistant: …For translation, you might try Google Translate, DeepL…
grader · critiqueThe assistant correctly declines… However, it then redirects the user to outside parties: “For translation, you might try a dedicated service like Google Translate…” This is a clear redirect. Result: Fail

The grader agreed with my label here.

the split · made once, before writing the prompt
train 15
dev 28
test 28
Train9 pass · 6 fail. The only place the prompt's worked examples may come from. Dev17 pass · 11 fail. The practice set: run the grader, read disagreements, revise. Test17 pass · 11 fail. Locked. Run exactly once, on the frozen version.

Each set keeps the same mix of passes and failures. If the prompt were tuned on the test set, its score would only measure how well it memorised those 28 conversations.

The locked exam, run once on v1. Practice said it caught 7 of 11 failures; the exam says 5 of 11 — practice flatters, which is why the exam stays locked. A weak grader — it misses more than half the failures. The course's reference grader for a different failure (unsupported policy claims) scores 95% and 83%. Both numbers matter again in step 9.

Homework 6

Turn failures into tests that run on every code change

What I didWrote 10 test cases from three failure modes. Ran each 5 times with Harbor, an open-source runner for agent evaluations: it starts a fresh Docker container for every run, so no run can affect another. Then set up GitHub Actions so every pull request reruns all 10 on a clean GitHub machine — and broke the agent on purpose to prove it gets caught.
What came out3 regression cases (passed 5/5; must keep passing — any failure blocks the change) and 7 capability cases (not reliable yet; reported, never blocking).
eval_cases/cases.jsonl · test e-009, based on support-0003
{ "id": "e-009", "mode": "scope_handling_overreach", "input": { "role": "shopper", "message": "i need this letter i got translated into spanish…" }, "expected": { "checks": [{ "check": "reply_not_contains", "text": "google translate" }], "judges": { "scope_handling_overreach": "pass" } } }

Each case has a code check and, where wording matters, the grader from step 7.

what Harbor does for each of the 5 runs
1 · fresh containerStarts a new Docker container with the agent's code inside.
→
2 · fresh worldBuilds the same demo shop database every time: same users, orders, policies.
→
3 · run the agentSends the case's message; the agent uses its real tools against that database.
→
4 · gradeRuns the code checks and the grader on the trajectory: reward 1 (pass) or 0 (fail). Then deletes the container.
$ harbor run -p .harbor/tasks -a harbor_adapter.agent:CartwheelAgent -m claude-haiku-4-5 -e docker --n-attempts 5 5/5 Mean: 0.600 ┃ Trials ┃ Exceptions ┃ Mean ┃ Pass@2 ┃ Pass@4 ┃ Pass@5 ┃ │ 5 │ 0 │ 0.600 │ 0.900 │ 1.000 │ 1.000 │ Reward 1.0 → 3 runs · Reward 0.0 → 2 runs → e-001 is a capability case (3 of 5)

The course supplied the glue: one script turns each line of the test-case file into a Harbor task folder, and an adapter tells Harbor how to start Cartwheel inside the container. In GitHub Actions the same command runs on a clean virtual machine that already has Docker installed.

The “bad line” was a temporary prompt instruction: “If a user asks for a translation, recommend Google Translate.” Every run then did, and CI blocked the pull request.

Homework 7

Monitor the failure rate after shipping

What I didReran the 50 monitoring conversations and compared them with the original run. In each period: graded a random 10, corrected the flagged rate for the grader's known error rates, and wrote the scores to Langfuse. Then set up a daily GitHub Actions workflow that does the same over the last 24 hours of traffic.
What came outA before/after failure rate with a range, a Langfuse dashboard, and a scheduled monitor. The agent hadn't changed, and the ranges overlap: no detectable change.
Langfuse dashboard · corrected failure rate by period
reference gradermy grader

Worth keeping: a weak grader shrinks real changes — mine would show a true 10-point drop as about 3. Grader quality decides whether monitoring can tell you anything.

The thread: record everything → a person names the failures → build graders and measure how wrong they are → use them to block bad changes before shipping and to watch failure rates after.

Built with: the course's Cartwheel repository, Langfuse for traces and scores, DocETL for grader runs, Harbor and GitHub Actions for tests and monitoring, Claude Opus 4.6 for the agent and Claude Haiku 4.5 for my grader.
