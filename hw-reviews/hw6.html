Putting the mistakes on a tripwire

Homework four found the mistakes and homework five built a grader for one of them. This week I turned them into ten test cases that run on every pull request, in fresh containers, five times each — then broke the assistant on purpose to see whether the tripwire would catch it.

Part one

What I did

  1. 1 Wrote ten cases from three of my homework-four mistakes: answering with the platform's return window when the store has its own, guessing which order a customer means, and sending people elsewhere for things the shop can't do. Each case is one customer message plus checks: exact ones in code (“no refund was issued,” “the reply mentions 14”) and a grader only where the wording matters.
  2. 2 Ran each case five times before deciding what it was. Five out of five makes a regression case — something that works and must keep working. Anything less makes a capability case — something the assistant can't do reliably yet. Three and seven.
  3. 3 Wrote the scoring. pass@k: the chance that at least one of k tries works. pass^k: the chance all k work. And the rule: a regression case that fails even once blocks the merge; a capability case never does.
  4. 4 Wired it into GitHub. Every pull request now gets a fresh machine that runs all ten cases five times in throwaway Docker containers and posts the table as a comment.
  5. 5 Broke it on purpose, then fixed it. One line in the assistant's instructions — “if a user asks for a translation, recommend Google Translate” — then reverted. Finally, ran one wobbly case fifteen times to see how much more runs change the picture.
Part two

What I learned

The worst case wasn't about words

It filed a $240 refund on a guess, fifteen times out of fifteen

Customer one has two vases from the same shop that could both be returned. Told “the vase arrived cracked, just refund it,” the assistant picked the newer one and submitted a refund for it without asking which. Fifteen tries across the baseline and both CI runs, and every one did the same thing: a $240 refund on order 4455.

A wrong sentence can be corrected in the next message. A refund on the wrong order is harder to take back.

What stopped the money moving was a safety rule, not the assistant's judgement: refunds over $100 wait for a person to approve them, so all fifteen landed in the approval queue. The other vase cost $84. Had it guessed that one, the refund would have gone straight through.

No grader is needed here either. The check reads the refunds table: was a refund created for either order? Plain code, no model, no ambiguity. It's the clearest target for the next module.

Regression doesn't mean reliable

A case that passed five out of five still failed

e-004 asks whether Saltbox Pantry uses the normal 30-day returns. It passed all five baseline runs, so it became a regression case. In the run with the bad line it failed once — the assistant said “30 days, check the store's page” instead of finding the 7-day store policy — and blocked the pull request on its own.

Five passes only says the failure is rare, not absent. If each of my three regression cases works 98% of the time, all fifteen runs pass about three times in four. So roughly one pull request in four would be blocked by noise. The course's rule is to keep that failure as evidence rather than rerun until it goes green, which is what I did.

Five runs is a small sample

The same case scored 3, 3, 1 and 2 out of 15

e-005 — return “the vase” when two match — passed 3 of 5 at baseline, 3 of 5 in the first CI run, 1 of 5 in the second, and 2 of 15 when I ran it fifteen times. Same code, same model. Any single batch of five could have told me anything from “works one time in five” to “works more often than not.”

Pooling every e-005 run I have gives 9 of 30, about three in ten. From ten runs to fifteen, pass@1 moved from 0.10 to 0.13 and pass@5 from 0.50 to 0.57.

Two numbers, two questions

“Can it ever?” is not “can I count on it?”

The taxes case, e-008, passed 1 of 5 at baseline. Its pass@3 is 0.60: give the assistant three tries and one probably lands. Its pass^5 is 0: five in a row never happened. A customer only gets one try, so the CI rule leans on the second view — any failure in a regression case blocks.

pass@k — capability

At least one of k tries works. Rises with k. Answers “is this within reach?”

pass^k — reliability

All k tries work. Falls with k. Answers “can customers rely on it?”

Graders miss things too

Code checks and the AI grader caught different failures

In e-001 the code checks passed all five runs — the reply said 14 days, as it should. The course's grader failed two of them for offering an unsupported “other options if it's damaged.” But it also passed a reply telling the customer to “reach out to Juniper Home Goods directly—merchants can make exceptions,” which is exactly my homework-four failure.

And in e-004 the grader passed the “30 days, check the store's page” answer; only the plain check for a “7” caught it. Neither layer is complete on its own, which is the case for using both.

Plumbing, briefly

Small substitutions, written down

I switched the assistant from Claude Opus to Claude Haiku 4.5, as the course now recommends: a frontier model rarely makes these mistakes, so there would be nothing to test. For wording checks I used my own grader on the scope cases and the course's reference grader (which runs on Claude Opus) on the store-policy cases.

Four fixes along the way: the pinned Harbor version writes its results one folder per run, so the course's summary script found nothing until it learned to read those files. My fork had GitHub Actions switched off until I allowed it on the website. The results table now posts as a pull-request comment instead of only on the run page. And the homework-four report test was written against the course's demo data, so it now skips — with the reason stated — for a student's own taxonomy.

Where it ended up. Ten cases in eval_cases/cases.jsonl — three regression, seven capability — running on every pull request. The deliberately broken run was blocked by e-009 (0 of 5) and, unplanned, e-004 (4 of 5); after the revert every case passed its rule and e-009 was back to 5 of 5. Fifteen runs of e-005 gave 2 passes.
