Evaluating and Improving AI Agents · Modules One and Two

How you find out what your agent gets wrong

Four assignments, one argument: you cannot improve an agent you cannot measure, you cannot measure it without recorded evidence, and you cannot interpret the evidence until a person has read some of it and said, in their own words, what bothers them.

1build the thing
2record what it does
3manufacture the evidence
4read it and name the faults
For the team

What this is, and why the order matters

These notes come from Evaluating and Improving AI Agents, a five-module course built around one worked example: a customer-support agent for a fictional marketplace, with a seeded database and a written specification. The example is fictional on purpose — every fact about every order is knowable, so you can check whether an answer was actually right instead of arguing about it.

The problem it addresses: agents fail quietly. A crash is obvious. An agent that confidently quotes the wrong returns policy, or tells a customer their refund is done when it is only queued, looks exactly like an agent that worked. Nobody files a bug, and the usual fix — reading a few conversations, adjusting the prompt, seeing if it feels better — has no way of telling whether the change helped or moved the failure somewhere else.

The course's answer is deliberately unglamorous, and the sequence is the argument:

Evidence before opinion

Record complete runs first. Every later claim has to point at a conversation someone can open.

Manufacture the evidence if you must

A new agent has no traffic. Plan the situations deliberately rather than asking a model for "some examples".

A person names the failures

Read real conversations and describe what's wrong in your own words, before inventing any categories.

Automate only after agreeing

Build an automated judge once you have human labels to check it against, not before.

Each step exists because the next is impossible without it: you can't analyse conversations you never recorded, can't name a pattern from one example, and can't trust an automated judge you never compared against a human. The payoff is that "the agent got worse this week" becomes a number with evidence behind it, and a prompt change can be shown to have helped rather than assumed to.

What it costs. Modules one and two are roughly the work described below: building and instrumenting the agent, generating a few hundred planned conversations, and one person reading a hundred of them closely. The reading is the part teams skip, and it is the part that produces everything else — the categories, the judges, and the numbers.

The arc

Why this order

Each assignment exists because the next one is impossible without it. You can't record what doesn't run. You can't analyse conversations you never had. You can't name a failure pattern from one example.

Homework one
Build

Get the agent working, and learn what it's made of

A support assistant for a marketplace: it looks up orders, quotes policy, issues refunds, cancels orders, escalates. The work is filling in the tools and then having enough conversations with it to know how it behaves.

The idea worth keeping: permissions and money live in code, not in the instructions. A prompt saying "never refund more than $100" is a wish. A tool that checks the amount and queues anything larger for a human is a rule. The model chooses which tool to call; the tool decides what is allowed.

That separation is what makes later analysis possible: when something goes wrong you can ask whether the model chose badly or the rule was wrong, and they need different fixes.

Homework two
Record

Instrumentation, or: you can't study what you didn't write down

Put the agent behind a proper front door that establishes who is asking, and make every request leave a durable record. A trace is one request. Inside it, spans are the steps: each model call, each tool call with its arguments and result.

Attributes

Labels attached to the record: who asked, in what role, which version of the instructions was in force. Without them you have transcripts you can't group.

Content capture

Whether the actual messages are stored, not just timings and counts. Off by default for good privacy reasons; you need it on to review anything.

Version stamping

Every record carries a fingerprint of the instructions used. Without it, comparing this week to last week is meaningless.

The idea worth keeping: recording is a design decision, not a switch. What you label determines which questions you can answer later, and you only find out you labelled the wrong thing when the question arrives.

Homework three
Generate

Manufacturing evidence worth reading

A new agent has no production traffic, so you make some. The naive version is asking a model for two hundred and fifty customer questions, and it fails in a specific way: the model writes the most typical request over and over. You get a hundred variations of "where is my order" and nothing at the edges, where the failures actually live.

Dimensions and tuples

Instead of asking for requests, you first name the dimensions — the ways one request can differ that change what the agent should do. Who is asking. What they want. What state the record is in. Which policy applies. How the person types. Then a tuple is one pick from each dimension: a single recipe for one conversation.

Why the answer key can't come from a model

Grounded expectations

For each planned conversation you write down what should happen before running it, and where that comes from: the order record, the rule that computes a return deadline, the store's policy page. If a model wrote the answer key instead, a confident wrong answer would grade as correct, and the whole exercise would measure nothing.

Some answers aren't a single fact — how to decline a request politely, say. Those get a written criterion citing the specification instead, and a person judges them.

Two sets, kept apart

Coverage

Ordinary requests spread across every dimension value. This is what a normal day looks like.

Challenge

Deliberately hard ones: rules that contradict the obvious, broken records, amounts a hair over a threshold, corrections mid-conversation.

They're counted separately, always. Mixed together, a pile of easy successes hides the failures at the edges — and because the challenge set is stuffed with hard cases on purpose, its failure rate is not a fact about production.

Pilot first, then the full set

plan → 30 scenarios → run → a human reviews → fix what's broken → 250 scenarios → run

The pilot is cheap insurance. Every scenario costs model calls to run, so it's worth discovering on thirty that your requests are repetitive, or that your answer key is wrong, rather than on two hundred and fifty. It also confirms the agent actually fails sometimes — a test set that everything passes teaches you nothing.

What the pilot caught here: three scenarios where the answer key said "cancel the order" but the generated customer had asked "can I cancel?". The agent answered the question it was asked. Marking that as a failure would have been a lie about the agent — the test was wrong, not the agent.

Homework four
Analyse

Reading the evidence, and naming what's wrong

Now you have hundreds of recorded conversations and an answer key. The temptation is to write a checklist of faults and start ticking boxes. Don't: you'll only find the faults you already imagined. The method goes the other way around.

Step one

Open coding: describe, don't classify

Read a conversation together with everything the agent looked up, and write a plain sentence about the first thing that's wrong. "The reply says the refund is processed, but the tool only queued it for approval." Not "tool problem" — a category name throws away the evidence that makes the fault definable later.

If nothing is wrong, write that down too. A reviewed trace with no failure is data; an unreviewed trace is a gap.

Why a purpose-built reading room

The generic annotation view fights you

Tracing tools are built for debugging one request, so they show a list of steps you click open one at a time. Reviewing a hundred conversations needs something else, and building it is part of the assignment:

Whole conversations

One trace per turn means a follow-up arrives with no visible history. Group them or you're reading fragments.

Thinking aloud vs. the reply

What the agent narrates to itself and what the customer actually reads are different things, and several faults only exist in one of them.

Notes pinned to evidence

Select the sentence, write the note, see it in the margin. The quote is what makes the note reusable later.

Case labels

Knowing what kind of case this is, and jumping to others like it, turns scattered reading into comparison.

Step two

Axial coding: group your notes, not your impressions

Lay out the notes you wrote and look for ones that would be fixed by the same change. That's the test — not whether they sound similar. Seventeen complaints about the agent narrating every step are one fault. Two complaints about quoting the wrong shop's policy are another. If two notes need different fixes, they're different faults even when the words look alike.

Each surviving fault needs a name, a yes/no test a stranger could apply, the notes it grew from, and examples. Five to eight of them is the working range: fewer and they're too vague to act on, more and they overlap.

The rule that makes it trustworthy

The person decides at every gate

An assistant can do the fetching, the grouping proposals, the counting and the searching. It must not decide what counts as a failure, and it must not invent a category from its own reading. A fault with no human note behind it isn't a fault, it's a guess with a tidy name.

In practice that's three gates: approve the dimensions before any data is generated, review a sample of conversations before spending money running them, and own every label in the final pass.

Step three

Hunting for more, and the near misses

Once a fault is named, you go looking for more of it — by filtering on a dimension you suspect, or by having the assistant search for conversations that look similar. Whatever comes back is a retrieval signal, not a label: you read each one and accept or reject it. The rejections matter as much as the acceptances, and both get saved.

Then, for each fault, you pick close negatives: conversations that look like the fault but aren't. A fault isn't really defined until you can point at the near miss and say why it doesn't count. Those boundary cases are what stop the definition drifting, and in the next module they become the hardest test cases for an automated judge.

Step four

Labelling: every fault, every trace, yes or no

Last comes the mechanical pass. For each conversation you reviewed and each fault in your final list, record present or absent — stored as a 1 or 0 against the trace in the tracing tool, alongside a local copy.

Two reasons it's worth the tedium. A conversation can contain several faults, and open coding stopped at the first one, so this pass finds the rest. And absence is data: a judge trained or validated only on failures flags everything, so the "no" labels are what make the "yes" labels meaningful.

The resulting percentages are fractions of what you read, not rates in the wild. You chose those conversations deliberately, so the number tells you the fault exists and roughly how it clusters — not how often a real customer meets it.

In short

The concepts, in one place

Trace & span

One request, and the steps inside it. The unit of evidence.

Dimension & tuple

A way requests differ; one pick from each dimension makes one planned conversation.

Expected result

What should happen, written down before the run and grounded in data, never in a model's opinion.

Coverage vs. challenge

Ordinary cases and deliberately hard ones, counted separately so neither hides the other.

Open coding

Free-text notes about what's wrong, written before any categories exist.

Axial coding

Grouping those notes into named faults, using "would one fix solve both?" as the test.

Close negative

A conversation that looks like a fault but isn't. It defines the boundary.

Retrieval signal

A search result proposing where to look. Never a verdict on its own.

Binary label

Present or absent, 1 or 0, per fault per trace. Compound quality scores can't be validated.

Sample fraction

How often a fault appeared in what you read. Not a prevalence estimate.

Where this is heading. Hand-reading doesn't scale, so the next module builds an automated judge for each fault and proves it agrees with the human labels before trusting it. Only then do the percentages become estimates you can act on — and only then is it worth changing the agent and measuring whether the change helped.

The thread running through all four: every number has to be traceable back to something a person read and decided.
