Evaluating and Improving AI Agents · Homework Three

Writing the answer key before the test

To find out where the assistant goes wrong, I needed a lot of conversations and, for each one, a written statement of what should have happened — worked out from the shop's own records rather than from anything a model said. Two hundred and fifty of them.

Part one

What I did

  1. 1 Decided what makes one request different from another. Who's asking, what they want, the state of the order involved, which shop rules apply, how hard it is, and how the person types. Deciding this first is what stops a pile of near-identical questions.
  2. 2 Worked out the right answer from the records. For each planned conversation a program looks up the real order, recomputes the return deadline with the same rule the shop uses, and refuses to continue if anything doesn't add up — the customer doesn't own that order, or the item they describe matches two of their orders.
  3. 3 Had a separate model write what the customer types — given only what that customer could know. Never the order number they don't have, never the delivery date, and never the answer. A second model then read each message back and checked it for invented details.
  4. 4 Ran thirty as a trial and read the results myself. Twelve reviewed properly, six genuine faults, three cases where my test was the thing at fault.
  5. 5 Built the full 250, ran them, and kept every recording. An hour unattended, about six dollars, and a file of 305 recordings ready to be studied.
Part two

What I learned

The idea underneath everything

If a model writes the answer key, the test can't fail

Ask a model to grade its own work and a confident wrong answer sails through. So nothing here is decided by a model. The return deadline comes from the delivery date and the shop's own window; whether a refund needs a human comes from a hundred-dollar line written in the rules file. A program computes each answer, records where it came from, and stops if the record doesn't match the claim.

It caught the first mistake before I'd spent a penny: one deliberately broken order is marked "not returnable" in the database while the rule says it is.

The moment it clicked

The test can be the thing that's wrong

Three of my trial conversations were unfair. I'd asked for a customer who wants to cancel an order, and the writer produced a perfectly natural sentence that asks whether they can. The assistant answered the question it was actually asked. My answer key said it should have cancelled.

What she typed

"can i cancel order #105? its a mechanical keyboard i ordered a couple days ago. just need a quick yes or no"

What I'd written down as correct

Cancel the order.

Marking that as a fault would have been a lie about the assistant. So it's recorded as my error, and every request-shaped conversation in the full set now says plainly what it wants. A separate check reads all 250 finished messages against their answers looking for the same mismatch.

What a batch of generated people sound like

Left alone, they all have the same cat

Asked for rambling customers, the writer produced four of them, two apologising for a cat on the keyboard, three opening with the same seven words. Fluent, plausible, and useless as variety — a set like that tests one kind of person over and over.

The fix that worked wasn't asking for more variety, it was showing each one what the others had already written and telling it to start differently. When two were rewritten at the same moment they couldn't see each other and both reached for the same excuse about a calendar app, so the last few had to go one at a time.

The reviewer that reads each message on its own can't catch this, because nothing is wrong with any single message. Only a comparison across the batch shows it.

The thing I nearly overclaimed

Six faults in twelve isn't a failure rate

Half the conversations I reviewed showed a real fault, and that number means nothing on its own. I chose which ones to read, and I started with the ones where the database told me something hadn't happened. A quarter of the whole set is deliberately nasty — broken records, rules that contradict the obvious, an amount twenty-five cents over the line where a human has to approve.

That's the point of the exercise: this set is enriched with hard cases, so it will always look worse than a normal day. The ordinary and the difficult are counted separately for exactly that reason, and what I have is a stock of faults worth studying, not a measurement of how often the assistant fails.

What the faults looked like

The interesting ones weren't wrong facts

  • faultAsked for a $282 refund, it explained the rule correctly and then asked permission instead of filing it. The customer service agent had already asked.
  • faultOn an order twenty-five cents over the approval line, it said "everything checks out, let me issue the refund" — never mentioning that a human has to approve it first.
  • faultAsked about a pencil set, it answered about a socket set, because the search it uses returns order numbers without the item names.
  • handledA product priced at minus five dollars: it called the price wrong rather than offering it.
  • handledA customer insisting for three messages: it held the line, and offered the thing it could actually do.

Most of these are the assistant being agreeable at the wrong moment, or being let down by a lookup that doesn't return enough. Naming and grouping them is the next assignment's job; this one just had to produce them.

Small things, learned the hard way

Four practical truths

Copy the command, not the placeholder. The instructions say --model YOUR_MODEL. Run that literally and all thirty conversations fail in about twenty seconds — harmlessly, but it looks alarming.

Check the date filter before believing an empty screen. The recordings viewer defaults to the last day. Four days after the run it showed nothing at all, and everything was exactly where it should be.

Reset the data before any run that changes it. The trial issued real refunds against the practice shop. Leave those in place and the next run's answers are computed from a world that no longer exists.

Generated details need to fit the thing they're about. My reason for wanting a refund was picked at random, which produced a journal that "stopped working" and a camp stove that "doesn't fit". Nobody writes that.

Where it ended up. 250 planned conversations with a recorded correct answer each, 175 ordinary and 75 deliberately hard, including five for every one of the six broken records. All 250 ran, 305 recordings exported, and a 50-conversation subset set aside to re-run later against an improved assistant.
